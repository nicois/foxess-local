## Context — how foxesslocal uses this package

foxesslocal is a single Go binary on *the gateway host*, the inverter's statically
configured gateway. It intercepts a Foxess KH10 inverter's proprietary
cloud uplink (framed binary over TCP/14431; the inverter is a non-
conformant TLS 1.2 client that trusts any CA — anchor T2, self-signed
cloud leaf with the 11-IP failover SAN set; details:
`docs/recon/protocol-profile.md` in the foxess repo) and replaces the
cloud's role locally: mode-level upstream policy — deny-all except `full`
mode and an active maintenance window (C-001/C-002; reworded 2026-11-13),
one validated command gateway
(upstream→inverter path, C-003), a self-owned REST API + web UI, a
scheduler, an SQLite audit store, and — at end-state C — serving the
inverter **with no upstream at all**.

The interception layer of that binary is **prox as an embedded library**:

- **Embedded mode** (`cfg.DataRoot == ""`): in-process, no capture files,
  no index.db, no retention; the capture registry still records.
- **TLS**: prox terminates the inverter leg with a leaf from the T2
  anchor (consumer-supplied via the leaf selector); the upstream leg
  mirrors to the real cloud per forward mode `off | telemetry_only |
  full`. At end-state C the flow runs serve mode `local` — the
  consumer-provided leg *is* the (simulated) cloud.
- **Policy = the hook chain.** foxesslocal registers hooks that:
  - inspect every chunk in both directions (R1) and apply the mode
    ladder to upstream-originated messages (C-001): deny-all (drop + audit +
    reason) except in `full` mode or an active maintenance window
    (2026-11-13 rewording — the per-message allowlist and the firmware hold
    were retired, so foxesslocal no longer uses the Hold verdict);
  - **inject** operator commands at arbitrary moments — Modbus
    read-modify-write pushes from the REST API/UI/scheduler (R2
    HookConn, C-003). Commands must not race the policy: the hook chain
    is the sole upstream→inverter path.
- **Audit**: foxesslocal's SQLite frame-level store keeps the raw bytes
  (our side); the capture stream (R6) is the *post-decision index* —
  which chunk, decided how, why, by whom. Provable audits need the
  index to be complete on its own terms (see G2/G3).
- **The egress gate is foxesslocal's** (C-007): nftables, default-deny on
  the inverter source IP; the tproxy diversion of port 14431 is **one
  rule inside that gate**. The gate is what makes "default-deny" airtight
  at the network layer.

So the package runs *inside our process*, under *our* firewall, with *our*
hooks doing the policy, and its capture stream feeding *our* audit store.

## Gaps (requests)

### G1 — (position R13, MUST) Consumer-owned capture rules

**The gap.** `Prox.Run()` unconditionally installs and removes iptables
TPROXY rules on its own lifecycle, through a hardcoded exec runner:

- `pkg/prox/prox.go:206-214` — `Run()` calls
  `rules.Remove(execRunner{}, params)` then `rules.Apply(execRunner{},
  params)` (and removes again on the way out), before listening. Not
  gated by embedded mode (`DataRoot == ""` runs the same path).
- `pkg/rules/rules.go` `BuildRules` — every capture command hardcodes
  `Bin: "iptables"` (plus `ip rule`/`ip route`); the `Runner` interface
  exists but the facade never accepts one — `execRunner` is the only
  implementation and it is unexported.

**Why it matters in our use.** The consumer owns the firewall (C-007,
nftables default-deny gate). A library that applies and removes its own
iptables ruleset inside the consumer's gate (a) fights for PREROUTING
ownership of the same port/mark, (b) can remove rules it believes are
its own at shutdown, and (c) cannot start in a deployment where the
diversion already exists — which is our deployment, from day one of the
embedded mode. Today the only way to use the facade in-process is to
let it manage iptables; foxesslocal will not take that.

**Shapes we would accept** (non-binding — prox's call): a consumer-
injected `rules.Runner` (or an equivalent seam) and/or a
"consumer owns the rules" mode in which `Run()` skips install/remove and
only requires that traffic reaches the listener. Either satisfies R13.

### G2 — (tracked as R6(a)) `capture.Chunk` carries no payload bytes

**The gap.** The post-decision capture record is
`{Dir, TS, Len, Decision, Reason, Origin}` —
`pkg/capture/capture.go:80-87`. No payload, no offset. In embedded mode
there are no `.bin` files, so the stream is the *only* byte-level source
the package offers; as it stands it is a decision index that cannot
point at bytes.

**Why it matters in our use.** The R6 contract is "capture and audit as a
first-class stream". foxesslocal's hooks store frames in their own
SQLite store (so the service works today — **G2 is not a blocker**), but
the *provable* record (what the capture stream says happened, vs what
our store holds) is weaker than it should be: a dropped chunk's bytes
exist nowhere in the package's own output, so a dispute about a policy
decision rests on our side's copy of the bytes.

**Request.** Carry the chunk's bytes in the record (or an equivalent: a
byte range the consumer can resolve). Size is bounded by the relay's
chunk unit (one read delivery / one TLS record on a MITM leg), so this
does not change memory behavior of anything that doesn't opt into the
stream.

### G3 — hook-drop records carry `Len == 0`

**The gap.** `Pipe.Data` records every decision, but the hook-drop path
omits the length — `pkg/hooks/hooks.go:361` records
`{Dir, TS, Decision: Dropped, Reason}` with no `Len`, while every other
decision path records it: close-drop (`:338`), hold (`:352`),
forward (`:369`), close-resolved held bytes (`:402`, `:462`). The dropped
chunk's size is known at the record site (`len(b)` is in scope).

**Why it matters in our use.** The post-decision index is the audit:
"C-002 held the 1024 B firmware chunk" vs "the policy dropped a
1024 B upstream push" — both must be provable from the record alone.
As shipped, a hook drop reads as a zero-length drop, which is
indistinguishable from a malformed record.

**Request.** Record the length on the hook-drop path (original chunk
length, consistent with how the other paths define it — prox to confirm
which `len` it considers canonical: the pre-chain chunk or the
last-transformed `cur`).

## Verified non-gaps (checked, no action wanted)

Recorded so the prox agent can see the boundary of this review:

- **`s2c_max_packet` vs the hook chain** — the cap sits *after* the
  chain and the capture tee (`pkg/proxy/ladder.go`, `s2cWriter`): hooks
  see every chunk, a hook drop takes precedence and the cap is never
  consulted, and a hook **Hold** of a firmware-sized chunk works — the
  11-09 experiment's failure mode (cap below the TLS flight size) is a
  raw-relay-era artifact, not a package defect. No change wanted.
- **Phase 2 surface present in v0.1.0** — serve modes (incl. `local`
  with the consumer leg), bounded hold with watermark + release, leaf
  selector, typed events, capture registry, embedded mode, drain. Our
  conformance check bodies for R3/R7b are pending (foxesslocal debt),
  not prox gaps.

## Clarification questions (confirm the contract, not requests)

- **Q1 — HookConn write order.** Hook writes are serialized with relay
  writes to the same direction, but their order relative to
  *in-flight* relay bytes is not contractually fixed (observed in our
  R6 check: an injection can land before a just-forwarded chunk).
  Confirm: is "no total order between injected and relayed bytes" the
  intended, stable contract? foxesslocal will rely on capture-record
  identity (origin/decision), not stream position, for everything —
  including command-ACK flows — but we want the contract explicit.
- **Q2 — Held bytes vs the cap.** When `ReleaseS2C` flushes a held chunk
  as one Forwarded record, does that chunk then pass through
  `s2c_max_packet` (the cap wraps the client-leg writer, so we expect
  *yes* — held bytes are not exempt)? foxesslocal will leave the cap at
  0 and do its own firmware hold, but the interaction should be stated,
  not incidental. *(Superseded operationally — see the 2026-11-13
  amendment above: foxesslocal no longer holds.)*
- **Q3 — Rule-removal ownership after G1.** Whatever shape G1 takes,
  confirm the shutdown contract: if the consumer owns the rules,
  `Run()`'s exit path removes *nothing*; if the consumer injects a
  runner, removal goes through that runner. (Stated so both sides
  implement the same side of it.)
